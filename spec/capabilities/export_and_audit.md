# Capability: Export and Audit

## What It Does

Allows users to download the filtered or aggregated results of any completed query as a CSV file, while maintaining a full audit trail of every query, its generated pandas code, execution result, and token usage in SQLite.

## Inputs

| Input | Type | Source | Required |
|-------|------|---------|----------|
| `query_id` | UUID string | URL path parameter on `GET /queries/{query_id}/export` | Yes |

## Outputs

| Output | Type | Destination |
|--------|------|-------------|
| CSV file download | `text/csv` binary | HTTP response body with `Content-Disposition: attachment; filename="query_{query_id}.csv"` |
| `exports` row | DB record: `{id, query_id, file_path, row_count, created_at}` | SQLite `exports` table |
| Export file | CSV file bytes | Local filesystem at `data/exports/{query_id}.csv` |

## External Calls

| System | Operation | On Failure |
|--------|-----------|------------|
| SQLite | Read `queries` row for `pandas_code` and `status` | Return HTTP 404 if query not found |
| Local filesystem | Write CSV to `data/exports/{query_id}.csv` | Return HTTP 500; do not create `exports` row |
| pandas | Re-execute stored `pandas_code` against loaded DataFrames to produce the export DataFrame | Return HTTP 422 with message `"Could not regenerate results"` |

## Business Rules

- Export is only available for queries with `status=completed`. Requesting export for a `pending` or `error` query returns HTTP 409 with message `"Query has not completed successfully"`.
- The export CSV is generated by re-running the stored `pandas_code` and writing the resulting DataFrame with `df.to_csv()`. If the result is a scalar (e.g. "total revenue is $X"), it is wrapped in a single-column DataFrame.
- The export file is written to `data/exports/{query_id}.csv` on first request and served from cache on subsequent requests for the same `query_id`. The `exports` row records `file_path` and `row_count`.
- The audit trail is built passively: every query stores `question_text`, `answer_text`, `pandas_code`, `reasoning_trace` (Phase 2), `input_tokens`, `output_tokens` (Phase 2), and `status` in the `queries` table from the moment of query creation through completion. No separate audit action is required.
- The full audit record for a query is accessible via `GET /sessions/{session_id}/queries/{query_id}` which returns all stored fields including `pandas_code`.
- Export files are never deleted automatically. The `data/exports/` directory is gitignored.
- Row count in the export: no cap (unlike the inline summary table which caps at 20 rows). The full result set is exported.
- The export endpoint does not require re-authentication (there is no auth in scope).

## Success Criteria

- [ ] Calling `GET /queries/{query_id}/export` for a completed query returns a valid CSV file with `Content-Disposition: attachment`.
- [ ] The downloaded CSV contains the correct filtered or aggregated rows matching the query result (not the raw uploaded data).
- [ ] Calling the export endpoint twice for the same `query_id` returns the same file (served from the cached `data/exports/` file on the second call).
- [ ] Calling export for a `pending` or `error` query returns HTTP 409.
- [ ] After any completed query, the `queries` table row contains non-null `question_text`, `answer_text`, and `pandas_code`.
- [ ] A scalar query result (a single number) exports as a single-row, single-column CSV.
- [ ] The `exports` row in SQLite is created on first export with the correct `row_count` matching the number of rows in the downloaded CSV.
